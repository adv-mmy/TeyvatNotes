# TeyvatNotes 软件需求规格说明书（SRS）

> 状态：基于 Pi Agent 的重做版需求文档。V1 至 V5 描述交付与验收目标。

## 1. 引言

**1.1 编写目的**  
明确重做版 TeyvatNotes 的产品范围、交付顺序和验收条件，供开发及测试使用。

**1.2 背景与目标**  
TeyvatNotes 是基于 Pi Agent 的原神攻略 Agent，以可交互的 `teyvatnotes` CLI 为入口。Pi 提供 Agent 运行时、模型与工具交互、会话和上下文管理。TeyvatNotes 负责攻略知识库、领域工具、玩家条件、引用校验与评测。

**1.3 术语**

| 术语 | 含义 |
| --- | --- |
| Pi Agent | TeyvatNotes 的运行时底座，提供 Agent Loop、工具调用、会话及扩展能力。 |
| Agent Loop | 一轮内向模型请求决策，执行已注册工具并把结果返回给模型，直至得到结果或满足停止条件。 |
| 会话事件日志 | 本地持久化的有序追加记录，用来重建会话历史与轮次状态。 |
| 模型上下文 | 从会话事件、系统提示词及本轮可用资料构建的模型输入，大小受预算约束。 |
| 合法证据 | 符合本轮范围、来自已发布且可追溯的攻略，并经本轮工具成功回读的证据。 |
| Skill | 带名称、描述和操作说明的本地任务指南，由 Agent 按任务选择加载。 |


## 2. 项目概述

- **产品入口**。用户通过 Docker Compose 进入交互式 `teyvatnotes` CLI，可提问、补充条件、查看工具活动与答案、继续已有会话。维护者通过同一 CLI 导入和维护攻略，开发者通过 Pi 的工具和扩展接口接入领域能力。
- **部署形态**。使用 Docker Compose 在一台主机上编排应用及本地依赖，主机无需单独配置 Node.js、Pi SDK 或数据库服务。V1 交付可运行的 CLI 容器；V2 通过 Compose 部署 PostgreSQL、ChromaDB 和 Ollama；V3 纳入 Redis。回答模型与联网资料源是独立的外部依赖。
- **首批攻略范围**。V2 首批只交付角色配队，覆盖通用配队和按已确认库存配队。用一个标准角色和一个明确的游戏版本做首批验收；角色名称、版本号与正式资料清单待确认（§8.5）。培养、配装、任务与解谜、机制问答另行排期，不作为 V2 通过条件。
- **V2 选型**。DeepSeek 开放平台的 `deepseek-flash`（Responses API）负责回答；联网配队资料从原神 BWIKI 的原生 MediaWiki API 发现与读取，不使用第三方搜索或 HTML 抓取。PostgreSQL 负责攻略原文和关键词召回，ChromaDB 负责语义召回，本机 Ollama 的 `qwen3-embedding` 生成向量，RRF 融合并重排两路结果。模型、资料源适配器与 Embedding 相互独立；变更须重跑相应验收。见[架构设计](architecture.md)。
- **重做范围**。新版交付采用 CLI 本地运行形态，退役 PySide6 界面、FastAPI 服务、HTTP/HTTPS 客户端协议、匿名令牌、IP 限流、旧客户端 SQLite 会话入口和 Windows 安装包。旧任务 API、Worker、SSE 同属退役范围。旧资料与会话如需迁移，另行定义独立工具和验收。
- **使用边界**。攻略库支持维护者导入资料，以及库内未命中时通过已配置的网络来源补充攻略。模型与 Embedding 可按配置访问获准服务。定时或批量采集、操作游戏客户端和公开服务部署另行立项。

## 3. 功能性需求

P0 对应 V1 的 CLI、Pi 工具循环与会话恢复。P1 对应 V2 至 V4 的阶段交付。P2 对应 V5 的增强候选，按实际需要排期。

| 编号 | 功能 | 优先级 | 阶段 |
| --- | --- | --- | --- |
| FR-001 | 交互式 CLI | P0 | V1 |
| FR-002 | Pi 接入与受限 Agent Loop | P0 | V1 |
| FR-003 | 工具注册、校验与执行 | P0 | V1 |
| FR-004 | 追加式会话与历史恢复 | P0 | V1 |
| FR-005 | 攻略导入、混合检索与联网补充 | P1 | V2 |
| FR-006 | 工具驱动的攻略问答与引用 | P1 | V2 |
| FR-007 | 上下文管理与压缩 | P1 | V3 |
| FR-008 | Skills 加载和使用 | P1 | V4 |
| FR-009 | 插件、钩子与事件扩展 | P1 | V4 |
| FR-010 | 运行体验、评测与外部扩展 | P2 | V5 |

### FR-001 交互式 CLI

用户可通过 Compose 启动交互式 CLI，新建和打开本地会话，用自然语言提交问题或补充条件。CLI 应展示追问、模型或工具的执行阶段、最终结果与可定位的错误。空白输入不启动一轮。没有模型连接或存储服务未启动时，用户仍可查看已保存的本地历史。

### FR-002 Pi 接入与受限 Agent Loop

每轮由 `teyvatnotes` 调用 Pi 会话执行。Pi 负责模型调用、工具分派及结果回送，模型根据工具结果决定下一步。TeyvatNotes 配置模型和可用工具，并执行领域校验、预算与停止规则。得到有效结果、条件不足、取消、不可恢复错误或预算耗尽时，应以对应状态结束。V1 通过真实 CLI 和 Pi SDK 接入受控模型及工具，验证完整循环，不依赖角色、游戏版本或攻略范围。真实模型连通与真实原神攻略回答不作为 V1 验收门槛，正式攻略问答从 V2 交付。

### FR-003 工具注册、校验与执行

工具通过 Pi 的自定义工具接口注册，提供名称、描述、参数约束和执行能力。TeyvatNotes 只暴露当前允许的工具，并在执行前校验名称、参数、范围和预算。未知工具、重复调用标识、无效参数、执行失败或超时均应产生可区分的结果。新增领域工具应复用同一注册入口。

### FR-004 追加式会话与历史恢复

复用 Pi 的本地会话与追加式记录，保存消息、工具交互及回答。TeyvatNotes 应关联本轮已确认条件、引用和轮次结局。重开会话时应恢复已保存历史和可继续使用的条件。未结束轮次应可识别为中断，继续操作由用户明确发起。模型上下文从会话派生，压缩和重建时保留原始记录。

同一会话换角色、版本或目标时，保留用户已经确认、且仍属于同一玩家的全局持有清单，包括明确空清单。角色专属条件（如命座或限定武器）只对对应角色有效；换角色不套用，换版本不沿用旧版本特有前提。换目标保留仍适用的已确认事实，清除不适用的目标约束；个性化目标缺少必要信息时重新确认。任务进度只在同一任务与适用版本下复用；换任务、换版本或进度冲突时先确认，任务场景不因此进入 V2 范围。新轮次重新检索和回读，旧轮引用记录保留，但引用资格不继承。

中断前用户已经明确确认且成功写入会话的条件保留；未确认、模型推断或未成功写入的修改不生效。恢复只重建状态，不自动重放旧轮工具。例如：

- 「角色 A 在版本 α 怎么配？我没有队友 B」后改问「版本 β 的角色 C 怎么配」：仍记得玩家没有 B，但不沿用 A 的命座限制、α 的攻略或旧引用；C 的必要条件未知时先问。
- 用户明确说「我其实没有队友 B」后取消：若该确认已写入，下次仍保留；若只是模型待确认的提取结果，不覆盖此前持有记录。

### FR-005 攻略导入、混合检索与联网补充

维护者可显式导入 Markdown 或 JSON 攻略。系统应保留来源与版本，完成解析、规范化、元数据校验、分块、Embedding 和索引，并区分校验失败、待发布与已发布。相同来源和内容重复导入应去重，更新保留旧版本与引用。

查询支持关键词和向量双路召回，按目标角色、攻略类型及 FR-006 的获准版本层过滤，以 RRF 融合并去重。库存不符或适用前提未知不阻止候选回读；当前可用性由答复阶段判断。

**联网判定。** 只有查询条件齐全、两路检索正常完成且合格候选为空、结果已经回送 Pi、本轮此前从未命中且未执行过联网补查时，才允许在后续批次调用 `search_web_guides`。普通配队问法无需用户指定工具或检索词；由 Pi 决定是否补查，应用使用已确认的角色生成实际请求，模型不提供参数。无可用的获准来源时，应提示来源受限，而非绕过权限。

| 情形 | 判定与行为 |
| --- | --- |
| 仅有其他游戏版本，或按本轮获准的版本及其他范围条件过滤后全部为空 | 两路检索正常完成才算 `miss`。符合其余门禁时，下一批可由 Pi 发起一次补查。错版本不作为证据；明确版本查询中，`null` 不算精确命中。 |
| 本轮查库命中 | 回读候选；本轮关闭外搜入口。之后改词搜空，或同批既有 `hit` 又有 `miss`，都不能重新开放。 |
| 库内命中但回读截断或正文不可完整读取 | 该窗口不可引用；可继续回读其他合格候选，仍无证据则说明缺口，不开放联网。 |
| 任一路检索异常、索引或依赖故障 | 返回检索错误，不以另一路结果或空结果模拟 `miss`，不发起外搜。 |
| 条件不足、Pi 未选择调用、或本轮已补查后重检未命中 | 分别追问、说明资料不足或报告补查缺口；不发起新的外部请求。 |

**发现候选、取得正文、发布与引用是不同状态。** 联网补查只走原神 BWIKI 原生 API；请求失败与正常无结果须分别反馈，不切换其他渠道。

| 检查点 | 通过条件与未通过处理 |
| --- | --- |
| 已发现候选 | 原生搜索只返回候选线索。应用固定允许的 API，Pi 只提供普通检索词，不能改写请求目标或来源范围。 |
| 可请求正文 | 原神 BWIKI 的公开攻略是项目认可的非商业资料来源，默认允许通过原生 API 自动检索、读取、存储和注明出处引用，不逐篇征求确认。页面另有许可或使用限制时从其声明；候选须符合配置的许可范围，且请求不跟随重定向。 |
| 已取得正文 | 有可读取、可定位且与指定修订和章节一致的原文；标题、摘要、图片或模板占位、拦截页和缺失正文不作为攻略证据。取得正文不代表已发布。 |
| 可进入自动发布流程 | 须有获准且可追溯的来源、原文链接及修订与章节定位、可读且相关的正文，以及可确认的目标标准实体和攻略类型。**识别出完整四人阵容和适用条件均不是 BWIKI 入库门槛。** 能核对的阵容和条件照实保留，未能确认的保持未知，不填作「无额外限制」。未明确声明的游戏版本记为 `null`，不得从搜索词、Wiki 修订号、网页日期或模型推断版本。角色或攻略类型无法确认，或明确的游戏版本声明相互冲突时，不发布、不检索、不引用；仅在允许存储时可保留为待补全记录。 |
| 索引就绪且已发布 | 去重、分块和向量索引完成，确认能查询到对应分块；满足前项后自动发布，不增加人工内容核验或审核。索引失败或尚不可查时不可发布，按错误或未就绪反馈。 |
| 可供本轮引用 | 发布后 Pi 按同一问题和已确认范围重检，成功回读完整合法证据，才可在本轮引用。网页直接返回、入库结果或搜索摘要均无引用资格。 |

### FR-006 工具驱动的攻略问答与引用

| V2 配队模式 | 开始检索前的必填条件 | 持有信息未知或明确为空时 |
| --- | --- | --- |
| 通用配队 | 标准角色、通用配队目标，游戏版本按下述规则选择；用户指定的场景或限制纳入范围，未指定场景时只给有证据支持的通用建议。 | 库存不是必填项，不因此追问。给出候选配队及其持有前提，不声称玩家拥有所需资源。明确表示某角色或装备不可用时，不把含该项的队伍说成可用。 |
| 按库存配队 | 标准角色、配队目标及下述版本范围。 | 优先展示已确认满足库存及适用条件的方案。缺角色、空清单、明确排除或未知持有不阻止查阅参考；确需确认时可询问，但不截断已有证据支持的参考答复。 |

**版本选择。** 用户问「最新」或未给出版本且无仍适用的已确认会话版本时，先用已确认适用于当前版本的攻略；没有时可用版本为 `null` 的攻略作参考。当前版本未核实时不得猜测，也不得把这类资料表述为已验证适用最新版。用户明确指定版本时只匹配该版本；正常查无匹配、但有其他条件合格的版本未知资料时，先问是否接受参考。只有用户明确同意后才展示这类资料，原请求版本不变；拒绝则报告资料不足。检索故障、未查完或回读截断不能视为正常未命中。

Pi 可用 `search_guides`、`read_guide` 和条件式开放的 `search_web_guides`。应用按同一条模型回复形成的批次核验权限，只使用此前已回送的查库状态与候选。禁止同批用新查库结果授权回读；`read_guide` 只接受批次开始前已回送的本轮同范围候选。同批含查库和联网时拒绝联网，即使上一批曾返回 `miss`。拒绝必须回传对应调用标识且不产生实际回读、外部请求或写入。Pi 在合法补查完成后按 FR-005 重检并回读；无可引用证据时说明资料不足。详见[轮次授权设计](design.md#31-轮次授权状态与批次校验)。

涉及攻略事实的答复必须有本轮合法回读作为依据。应用校验证据是否符合本轮版本范围，并校验引用位置、原文摘录和已确认库存；能定位的引用不等于原文支持结论。最终答复实际引用任一版本为 `null` 的攻略时，引用显示「版本未知」，程序在文末追加一次「该攻略版本未知，请注意时效性」；仅检索或回读但未采用时不加。同范围证据有未解决冲突时，应说明分歧并引用已回读的冲突证据，不把一方表述为唯一确定的结论。下阶段若交付任务攻略，应在证据足够时给出前置条件、有序步骤和完成标志。

**先给配队思路，整队可选。** 有可信资料时，先用自然语言说明可确认的队友选择、队伍分工及相关限制，并给出引用；即使没有整队，也算完成有依据的回答。可另外给出综合本轮攻略形成的四人配队建议；不要求回到原文核对四人是否曾被列为同一队，不得把综合搭配说成原文明示。已知适用前提照实展示；未知只提示「适用条件未确认」。明确缺项或排除的方案只作参考并说明冲突；按库存模式优先展示库存及适用前提均确认满足的建议。没有可用证据才提示资料不足，不为补出整队额外调用模型。

### FR-007 上下文管理与压缩

在 Pi 的上下文管理和压缩能力上增加攻略领域约束。提交模型前应统计或保守估算 Token，并保留近期必要消息、已确认条件、合法证据，以及工具调用与结果的对应关系。达到阈值时可裁剪非关键结果或压缩早期历史。摘要应与原始证据的引用资格分开处理。仍无法满足预算时应停止并说明原因。原始历史保持可查，压缩使用的额外模型调用纳入预算。

### FR-008 Skills 加载和使用

复用 Pi Skills，从受控目录加载原神攻略场景的 `SKILL.md`。Agent 可根据任务选择相关 Skill，按需加载正文。首批可用配队或角色培养场景验收。重复名称、格式错误和加载失败应可诊断。Skill 提供任务指导，工具权限由 TeyvatNotes 校验。

### FR-009 插件、钩子与事件扩展

通过 Pi 的扩展与事件接口，支持显式启用可信领域插件。至少验证一个新增工具和一个监听器经该入口接入。CLI、诊断和评测可订阅所需的轮次、模型、工具、压缩与终止事件。运行事件与持久化会话记录的保留范围应明确。

### FR-010 运行体验、评测与外部扩展

V5 可按需求加入流式交互、运行中引导或追加输入、受控重试、追踪和独立评测运行器。评测需分别记录检索命中、有效回读、引用支持、任务完成、延迟与用量，区分模拟和真实结果。MCP、子智能体和多智能体调度在单 Agent 链路稳定后独立评估。最小回归用例随前序阶段交付。

## 4. 非功能性需求

| 编号      | 类别      | 要求                                                                                         |
| ------- | ------- | ------------------------------------------------------------------------------------------ |
| NFR-001 | 有界执行 | 可分别配置单轮模型次数、工具次数、外部调用次数、Token、单步超时和总时限。达到边界或收到取消后结束本轮，不启动后续调用。实际已报告用量与本地估算分别记录。 |
| NFR-002 | 可靠性     | 工具、模型协议、存储和预算故障应有稳定分类。记录实际轮次结局，避免挂起或对失败请求静默重放。未来启用重试时须明确范围、次数及副作用约束。                       |
| NFR-003 | 安全与隐私   | 模型凭据由本地配置提供，禁止进入普通日志、会话导出及工具参数。用户输入、攻略及模型输出按数据处理。只有显式授权的工具和插件可以执行，不默认开放命令执行、任意文件访问或任意网页访问。 |
| NFR-004 | 可诊断与可评测 | 运行事件可关联到会话、轮次和工具调用，记录阶段、耗时、用量及错误分类。普通诊断输出应脱敏。各阶段支持用固定资料和模拟模型复现。                            |
| NFR-005 | 可维护性    | Pi 接入与攻略存储、检索规则、证据校验保持接口隔离，以便单独测试和复用领域实现。 |
| NFR-006 | 可部署性 | 各阶段应提供可复现的 Docker Compose 配置及启动、初始化和停机说明。默认不发布数据库等内部端口；凭据在运行时注入，不打进镜像。重建容器应保留会话、攻略与索引。 |

## 7. 业务规则与约束

- **BR-001 Pi Agent 底座**。TeyvatNotes 基于 Pi Agent 运行，在其上提供攻略领域规则、工具、知识检索、引用及评测。
- **BR-002 证据与版本**。正式攻略回答仅引用范围内已发布、非虚构且本轮完整回读的资料。联网内容须同时满足 FR-005 的来源许可、最低元数据和索引就绪要求才自动发布。搜索摘要、压缩摘要和模型自报链接均不能作为原文证据，引用位置从资料记录生成。
- **BR-003 权限与执行**。Pi 会话只启用本轮获准的工具。默认禁用通用编码工具和未登记扩展。TeyvatNotes 执行参数、数据范围、终止规则和预算校验，并使 Pi 的自动续跑与重试配置遵守 NFR-002。Skill 内容和外部资料不能授予额外权限。
- **BR-004 数据边界**。攻略数据与私有会话分开管理。旧数据保留在原位置，单独批准迁移后才写入目标环境。
- **BR-005 技术约束**。V2 将攻略正文和引用元数据与向量索引分别存储，两路召回按范围过滤后由 RRF 合并并排序。联网补充的攻略须在索引可查询后发布，供本轮重新检索。存储选型见 [架构设计](architecture.md)。

## 8. 验收标准

### 8.1 分阶段交付

1. **V1 Pi 最小集成**。通过 Compose 启动 `teyvatnotes`，用受控模型和工具验证调用、结果回送、停止和 CLI 容器重建后的会话恢复。不以真实模型、真实攻略问答或 V2 依赖作为门槛。
2. **V2 攻略 RAG**。通过 Compose 启动 PostgreSQL、ChromaDB 和 Ollama，用首批角色案例跑通导入、索引、混合检索、回读和引用，并核对容器重建后攻略与索引仍可复用。V2 须交付联网检索与自动入库：本地真正未命中时，从 BWIKI 获准范围内搜索并读取合格攻略，完成发布、当轮重检与引用，后续轮次可直接复用。本期不以明确版本的正式样本为交付门槛；保留既有版本范围规则及自动化回归。AT-10 同时要求模拟回归与真实来源隔离验收，两者不能互相替代。
3. **V3 上下文管理**。在 Compose 中接入 Redis，用长会话和大工具结果验证组装、预算、裁剪与摘要。缓存不可用时核对本地重建、原始历史和关键条件。
4. **V4 可扩展性**。验证按需加载 Skill，新增工具和监听器可通过约定接口接入。
5. **V5 增强**。为选入范围的增强能力另定用例，按真实启用的模型与工具记录效果。

### 8.3 V2 固定回归样本与通过标准

以下是确定性的隔离用例规格。A 为询问角色，B、C 为队友，α、β 是两个互斥的测试版本；这些标记及样本结论只用于测试，不是原神事实，不进入正式库。每个用例固定输入、初始库及会话状态、人工标注的参考分块和预期行为；实现时记录语料修订和哈希，不按实际排名回填参考答案。正式资料验收集及阈值见 §8.5。

| 样本 | 固定输入和资料 | 通过条件 |
| --- | --- | --- |
| V2-P01 通用配队 | 问 A／α 的通用配队，库存未知。α 的资料 `G-01#team` 推荐 B，并明确前提 P。 | 不因库存未知追问；给出 B 和前提 P，不声称玩家持有 B；引用定位到 `G-01#team` 并支持建议。库内命中时外搜为零。 |
| V2-P02 个性化替换 | 问 A／α，并确认持有 A、C、不持有 B。`G-02#alt` 在相同目标下给出 C 的可行替代及前提。 | 优先给有原文支持且符合已确认条件的 C；不把含 B 的队伍说成可用。 |
| V2-N01 错版本 | 问 A／α，库内只有 β 的 `G-03#team`。 | 不引用 β；两路正常完成时返回 `miss`。该固定用例中 Pi 选择不联网，最终资料不足，外部请求为零。 |
| V2-N02 持有为空或未知 | 目标角色未持有、空清单、未知持有或明确排除，有合格的配队资料。 | 均能回读并展示配队思路和可选的参考建议；明确冲突和未知分别提示，不标为当前可用。 |
| V2-N03 无证据或伪引用 | A／α 查库命中但回读截断；另测模型以搜索摘要或非本轮 ID 当引用。 | 不输出有证据支撑的确定结论；非法引用被拒绝，截断不触发外搜。 |
| V2-N04 冲突攻略 | `G-04#team` 与 `G-05#team` 对 A／α、同一前提 P 的队伍结论相反。 | 回读双方仍无法解释冲突时，指出分歧并定位原文，不单选一篇给唯一确定建议。不能以 RRF 名次判定对错。 |
| V2-P03 当轮补查 | 库内无 A／α；模拟 OpenSearch 返回获准与未获准候选，获准候选经两次 Parse 获取固定修订下的 `G-06#team` 正文。另测未声明游戏版本、版本声明冲突及索引未就绪；部分证据另见 V2-P05。 | 仅获准候选触发 Parse；索引可查再发布。下一批重检，完整回读后引用；另起一轮直接命中且零外部请求。未声明版本可按 `null` 发布，但不算指定版本命中；版本冲突或索引未就绪不发布。 |
| V2-P04 未知版本参考 | 库内有 A／α 的攻略和合格的 `null` 攻略，α 为已确认当前版本。分别问最新、未指定版本、明确问无匹配的 β；设置仅有 `null` 的变体，并分别同意与拒绝参考。 | 最新或缺版本先用 α；仅有 `null` 时可参考。找不到 β 时先询问，未同意不得用 `null`；拒绝则资料不足。答复使用 `null` 时引用显示「版本未知」，文末仅提示一次；未使用则无提示。 |
| V2-P05 BWIKI 部分证据 | 资料只有队友、分工或限制，没有原文四人队；对照模型给出思路加综合阵容、只给思路、适用条件未知及伪造引用。 | 两种有证据的答复均正常展示，思路先于可选配队建议；不要求原文列出同一阵容，不把模型组合标成原文推荐。未知前提只提示，非法引用仍拒绝。 |

每个固定回归用例按预期状态与禁止行为逐条判定，不能用平均分掩盖错版本、越权抓取、虚假引用、未持有角色被当成可用或无证据的确定结论。**程序定位校验**核对本轮完整回读、链接、版本、位置和摘录。攻略事实的**原文支持质量**由参考标注或人工比对；综合配队按是否合理使用证据、是否明确标为建议验收，不核对四人是否在原文中组成过整队。正式质量、耗时与成本门槛待定。

### 8.4 V2 补查用例的预算口径

固定正例 V2-P03 使用分批路径：查库 → 联网 → 重检 → 回读 → 最终答复。基准轨迹含 **5 次模型请求、4 次合法工具执行、1 次候选发现（OpenSearch）和 2 次读取（Parse）**。每个外部 HTTP 请求分别计数，不额外计为 Pi 工具执行；分块、Embedding、索引写入与可见性检查的耗时仍计入本轮。这是用例计数，不是产品上限。

从开始受理非空输入到终态，使用同一个总时限。模型、工具、候选发现和读取请求分开计数、各受单步超时约束；工具内的外部请求还受工具和整轮剩余时限约束。已发出的请求失败也计数；被拒的工具请求另记，不得有回读、出站或写入。记录实际用量、Token 估算和耗时。固定用例另测两次 Parse 之间或重检前耗尽预算：明确停止，不发下一步请求、不自动重试，未完成索引的资料不可发布。上限与具体超时数值见 §8.5。
