# 攻略回答验收标准：后续实现规格草案

日期：2026-10-03。本文件定义完整目标，需区分当前实现与后续验收。

已补齐无模型证据准备、独立单轮回答、通用 Responses 适配器、受限工具循环、RAG 基础和私有会话；JSON/引用存在性/显式资源限制通过程序校验，见 [模型与回答说明](model-answering.md) 和 [工具循环](tool-agent.md)。另有 [离线虚构流程评测与可靠性演示](evaluation.md)，不等于真实 API 或答案质量验收。准备入口的 `evidence_ready` 仍非 `answer`；真实语义、事实审核、费用和流式回答等完整规格尚待完成。

## 1. 首版范围

先选择一个明确游戏版本、一个角色和一条任务，使用少量经过审核的资料跑通闭环；再扩至 2～3 个角色、2～3 条任务、20～30 个来源。具体对象和来源待用户确定；平台与模型通过 `LLM_BASE_URL` 和 `LLM_MODEL` 显式选择，不在代码中固定，当前只支持 Responses 兼容协议。此前本机选用 OpenASI/Sol 的结果保留为历史记录。接口验证状态见模型说明，不能当作真实攻略质量验收。密钥不发送到聊天、不进入代码、日志或 Git。

## 2. 输出契约

回答类型分为 answer、needs_clarification、insufficient_evidence。

- 给出使用的玩家条件、游戏版本和必要假设。
- 角色建议包含目标、配队/装备条件及玩家现有装备的替代方案。
- 任务回答包含前置条件、有序步骤和完成标志。
- 每项关键结论绑定知识库已有证据 ID，由程序拼接来源链接和位置。
- 区分资料事实、作者推荐、条件性推断、冲突和未知项。
- 缺少地点、进度、装备或版本等关键条件时追问，不编造玩家档案。

追问结束本次调用。玩家补充条件后发起新一轮问答，由会话保存已确认的条件。

## 3. 工具、预算与安全

先手写 search_knowledge 与 read_evidence 两个只读工具；需要时增加可追溯的结构化资料查询。模型只能提出调用，程序负责名称白名单、参数校验、执行和稳定错误。

模型轮数、工具调用、单次/总超时、输出 Token 和费用需有界；跨 attempt 使用同一任务预算。重试可能重复计费，不能声明恰好一次外部调用。

引用存在性和装备限制由程序检查，证据是否支持结论要单独评测。工具权限和预算由程序控制。玩家条件、回答和会话历史需要按所属用户隔离。

## 4. 固定评测

逐步形成约 50 条问题：15 条角色、15 条任务、10 条条件不足、5 条资料冲突、5 条范围之外。分开发集与保留验收集，记录模型、提示词、资料版本及成本口径。

当前已落地相同数量分组的虚构流程回归，30/20 两组共用同一小型虚构语料；当前 45 题流程通过、5 道冲突题失败。它不能代替上述真实问题/独立保留集与人工语义验收，也不能把未知费用或未检查的事实标成通过。

每条保存输入、参考证据、检索结果、工具调用、最终回答和失败原因。检查检索命中、版本、玩家条件、步骤顺序、引用支持、缺口表达、费用及延迟。

验收集内的编造机制、错误版本、无效引用和遗漏关键前置条件作为发布阻断项；不要用结构校验成功或检索有结果替代答案质量验收。
