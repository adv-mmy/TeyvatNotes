# 攻略回答验收标准：后续实现规格草案

日期：2026-10-03。本文件定义完整目标，需区分当前实现与后续验收。

已补齐无模型证据准备，以及独立的单轮回答 CLI、OpenASI Responses 适配器、JSON/引用存在性/显式资源限制校验，见 [模型与回答说明](model-answering.md)。这些通过模拟测试，不等于真实 API 或答案质量验收。准备入口的 `evidence_ready` 仍非 `answer`；工具调用循环、真实资料评测等下述完整规格尚待完成。

## 1. 首版范围

先选择一个明确游戏版本、一个角色和一条任务，使用少量经过审核的资料跑通闭环；再扩至 2～3 个角色、2～3 条任务、20～30 个来源。具体对象和来源待用户确定；模型服务商为 OpenASI，用户因旧 Terra 分组无可用通道而明确改选 gpt-5.6-sol。接口验证状态见模型说明，不能当作真实攻略质量验收。密钥不发送到聊天、不进入代码、日志或 Git。

## 2. 输出契约

回答类型分为 answer、needs_clarification、insufficient_evidence。

- 给出使用的玩家条件、游戏版本和必要假设。
- 角色建议包含目标、配队/装备条件及玩家现有装备的替代方案。
- 任务回答包含前置条件、有序步骤和完成标志。
- 每项关键结论绑定知识库已有证据 ID，由程序拼接来源链接和位置。
- 区分资料事实、作者推荐、条件性推断、冲突和未知项。
- 缺少地点、进度、装备或版本等关键条件时追问，不编造玩家档案。

追问结果结束本次任务，不保持 Worker 等待用户；后续补充开启新的问答任务，早期 CLI 显式携带已确认条件。

## 3. 工具、预算与安全

先手写 search_knowledge 与 read_evidence 两个只读工具；需要时增加可追溯的结构化资料查询。模型只能提出调用，程序负责名称白名单、参数校验、执行和稳定错误。

模型轮数、工具调用、单次/总超时、输出 Token 和费用需有界；跨 attempt 使用同一任务预算。重试可能重复计费，不能声明恰好一次外部调用。

引用存在性和装备限制由程序检查，证据是否支持结论要单独评测。来源资料是数据，不能改变系统权限或工具预算。接入玩家上下文前必须保护攻略任务、列表、SSE 与会话读取，现有公开读取策略不能直接沿用。

## 4. 固定评测

逐步形成约 50 条问题：15 条角色、15 条任务、10 条条件不足、5 条资料冲突、5 条范围之外。分开发集与保留验收集，记录模型、提示词、资料版本及成本口径。

每条保存输入、参考证据、检索结果、工具调用、最终回答和失败原因。检查检索命中、版本、玩家条件、步骤顺序、引用支持、缺口表达、费用及延迟。

验收集内的编造机制、错误版本、无效引用和遗漏关键前置条件作为发布阻断项；不要用结构校验成功或检索有结果替代答案质量验收。
